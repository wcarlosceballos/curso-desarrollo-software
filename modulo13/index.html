🔐 M13 · Seguridad web

Este es el módulo más importante del curso para tu cliente, y el que casi nadie aprende por su cuenta.

El motivo es sencillo: los dos módulos siguientes ya son la mitad del camino si no hay seguridad. Y tú vas a poner en manos de un tercero —una ferretería, un consultorio— datos que son de esa persona.

⚠️ La Ley 1581 vuelve a aparecer aquí

En M3 te pedí autorización por escrito para usar datos de tu cliente. Eso era para no meterte en un problema legal. Este módulo es para que los datos no se filtren: la otra mitad del mismo asunto.

Qué sales sabiendo hacer

  • Guardar contraseñas sin guardarlas en texto plano.
  • Proteger las consultas a la base de datos contra inyección SQL.
  • Entender por qué "ocultar el campo con JavaScript" no es seguridad.
  • Separar lo que es secreto del código, para que no acabe en GitHub.

Las cinco cosas que importan

1 · Las contraseñas nunca en texto plano

Si guardas "contraseña123" tal cual, quien lea tu base de datos tiene todas las contraseñas de todos los usuarios. No es un riesgo teórico: es exactamente lo que pasa cuando filtran una base.

Se guardan hasheadas. Un hash es una función de una sola dirección: no se puede deshacer. Tú guardas el hash, y comparas hasheando lo que el usuario escribe.

// lo que guardas
$2b$12$KIX3dFzKJH8XqWjNQf2bS.8nK9Lh3vQdEeVvB6XkQZ0mN0pTqK

// lo que nunca guardas
contraseña123

Usa una biblioteca que ya lo hace: bcrypt o argon2. No implementes el algoritmo tú mismo. Nunca.

2 · Inyección SQL

El ataque más famoso de la historia de la programación, y el más fácil de prevenir.

El problema: si metes lo que el usuario escribió directo dentro de una consulta SQL, quien escribe ' OR '1'='1 en un campo de contraseña entra a todo.

La solución se llama consultas parametrizadas o consultas preparadas: el valor del usuario viaja separado de la instrucción, así que nunca se interpreta como código.

// NUNCA — concatenar
query = "SELECT * FROM usuarios WHERE pass = '" + entrada + "'"

// SIEMPRE — parametrizar
query = "SELECT * FROM usuarios WHERE pass = ?"
ejecutar(query, [entrada])

Si tu framework tiene forma de consultar que no sea concatenar, úsala siempre. Casi todos los frameworks modernos resuelven esto por ti si no lo haces mal.

3 · No confíes en el cliente

Cualquiera puede editar el JavaScript de tu página desde las herramientas del navegador. Si tu validación está solo en el frontend, no existe.

El frontend es para laexperience; el backend es para la seguridad. Todo lo que importe, se comprueba en el backend. Siempre.

4 · XSS: no insertes lo del usuario como HTML

Si haces innerHTML = textoDelUsuario, quien escriba <script>...</script> ejecuta su propio código en tu página. Se llama XSS.

Usa textContent en vez de innerHTML cuando el dato viene de alguien. Es un cambio de una palabra que evita el ataque completo.

5 · Los secretos no van en el código

Contraseñas de base de datos, llaves de API, tokens: van en variables de entorno, nunca en el archivo.

⚠️ El error que más careers cuesta

Subir una contraseña al repositorio. Y se puede arreglar, pero hay que rotarla: Git guarda el historial para siempre, y aunque borres el archivo, la contraseña queda en los commits anteriores y en cualquier clon que alguien haya hecho.

Por eso existe .gitignore, y por eso el curso Git insiste en el módulo 5.

Lo que este módulo no te da

Autenticación completa —tokens, sesiones, recuperación de contraseña, doble factor— es un tema de varios días y cada framework lo hace distinto.

Lo que sí te llevas es entender los riesgos y saber qué preguntar. Eso es lo que separa a alguien que programa de alguien que entiende por qué lo que programa no se rompe el primer día.

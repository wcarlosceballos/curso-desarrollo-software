🔷 M7 · Programación a objetos

Sales de este módulo sabiendo organizar tu código en piezas con responsabilidades claras, y sabes explicar con un diagrama qué hace cada pieza.

El problema aparece siempre igual: el proyecto crece, las funciones se llaman unas a otras, y llega el día en que para cambiar el precio de un producto tienes que editar siete archivos. Eso no es un error de lógica: es un problema de estructura, y por eso existen los objetos.

La programación a objetos es una forma de pensar, no un requisito que alguien te impone. Un archivo que hace una sola cosa, bien nombrado, ya está bien organizado aunque sea un procedimiento. Los objetos aparecen cuando el sistema tiene entidades con datos y comportamiento: un cliente, una orden, una factura.

Qué vas a aprender

  • Clase y objeto: la clase es el molde, el objeto es la pieza concreta. Producto es la clase; cada producto que registras es un objeto.
  • Atributos y métodos: lo que el objeto es y lo que el objeto hace.
  • Encapsulamiento: los datos se cambian con métodos, no por la puerta de atrás. Por eso el código no se rompe tanto.
  • Composición: un objeto que contiene otros. Una orden tiene líneas de pedido.
  • Herencia: una clase que empieza donde otra termina. Úsala con cuidado: es la relación más fácil de usar mal.
  • Interfaces: el contrato que debe cumplir una clase, sin importar cómo lo haga por dentro.
  • SOLID: cinco principios para que el código sea fácil de cambiar. Conocidos; no adorados.
class Orden {
  constructor(cliente, lineas) {
    this.cliente = cliente;   // composición: la orden "tiene" un cliente
    this.lineas = lineas;
  }
  total() { return this.lineas.reduce((t, l) => t + l.precio, 0); }
}

Composición o herencia

La regla práctica: si dices "es un", probablemente sea herencia. Si dices "tiene un", es composición. Y fíjate en qué estás dudando: cuando dudas entre herencia y composición, casi siempre conviene composición. Permite cambiar las piezas sin arrastrar a los hijos, y nadie termina heredando de una clase que un día hay que cambiarle todo.

Sobre SOLID: leer los cinco principios está bien. Aplicar los cinco a un proyecto de 300 líneas es sobre-ingeniería. Aplicarlos cuando el código ya te está doliendo es exactamente lo que toca.
